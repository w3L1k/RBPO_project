# Требования безопасности Campus Helpdesk

## Область действия

Требования относятся к серверному API Campus Helpdesk и учебным данным,
описанным в [паспорте проекта](../PROJECT.md). Критерии ниже задают наблюдаемое
поведение. До фактического выполнения тестов они являются планом проверки, а не
свидетельством реализации.

<a id="sr-01"></a>

## SR-01 — Серверное определение идентичности

**Свойство.** Для каждого защищённого запроса сервер устанавливает участника и
роль только по успешно проверенному аутентификационному контексту. Переданные
клиентом поля `author_id`, `user_id`, `role` или их аналоги не могут изменить
автора действия.

**Обоснование.** Доверие идентификатору из тела запроса позволяет действовать от
имени другого пользователя или специалиста.

**Критерии приёмки.**

1. Запрос без действительных учётных данных к защищённому endpoint получает
   `401` и не изменяет данные.
2. Если аутентифицированный пользователь передаст чужой идентификатор автора,
   созданный объект всё равно будет связан с идентичностью из проверенного
   контекста либо запрос будет отклонён.
3. Роль из тела или параметров запроса не влияет на решение об авторизации.

**Связанные угрозы:** [T-04](THREAT_MODEL.md#t-04),
[T-07](THREAT_MODEL.md#t-07).  
**Проектное решение:** [D-03](SECURITY_DECISIONS.md#d-03).

<a id="sr-02"></a>

## SR-02 — Объектный доступ к обращениям

**Свойство.** Пользователь `User` может читать и изменять только собственные
обращения. Специалист получает доступ только в пределах очереди и рабочих
операций, разрешённых его роли; право проверяется для каждого обращения, а не
только при отображении списка.

**Обоснование.** Последовательные или угаданные идентификаторы не должны давать
доступ к чужому обращению.

**Критерии приёмки.**

1. `User A` получает своё обращение по его идентификатору.
2. `User B` при запросе того же идентификатора получает `404` или `403` без
   раскрытия содержимого и без изменения обращения.
3. Проверка применяется также к добавлению сообщения и повторному открытию, а
   не только к операции чтения.

**Связанная угроза:** [T-01](THREAT_MODEL.md#t-01).  
**Проектное решение:** [D-01](SECURITY_DECISIONS.md#d-01).

<a id="sr-03"></a>

## SR-03 — Конфиденциальность внутренних заметок

**Свойство.** Создавать и получать внутренние заметки могут только участники с
ролью `Specialist`. Поля внутренних заметок не включаются в пользовательские
ответы API, списки, сообщения об ошибках и публичную историю обращения.

**Обоснование.** Служебные заметки могут содержать детали диагностики и оценки,
не предназначенные для автора обращения.

**Критерии приёмки.**

1. Специалист может добавить заметку и затем получить её в служебном
   представлении обращения.
2. Автор обращения получает публичное представление без текста, идентификаторов
   и иных полей внутренних заметок.
3. Прямой запрос `User` к endpoint заметок отклоняется и не подтверждает наличие
   конкретной заметки.

**Связанная угроза:** [T-02](THREAT_MODEL.md#t-02).  
**Проектное решение:** [D-01](SECURITY_DECISIONS.md#d-01).

<a id="sr-04"></a>

## SR-04 — Разрешённые переходы состояния

**Свойство.** Состояние обращения изменяется только серверной операцией,
разрешённой для текущего состояния и роли:

- `OPEN → IN_PROGRESS` — специалист принимает обращение;
- `IN_PROGRESS → CLOSED` — ответственный специалист фиксирует решение;
- `CLOSED → REOPENED` — автор обращения сообщает, что проблема сохранилась;
- `REOPENED → IN_PROGRESS` — специалист возобновляет обработку.

Произвольная установка состояния клиентом запрещена.

**Критерии приёмки.**

1. Каждый разрешённый переход в правильном контексте завершается ожидаемым
   новым состоянием.
2. Переход с неправильной ролью, владельцем или исходным состоянием получает
   `403` или `409` и не меняет запись.
3. Пропуск обязательного промежуточного состояния, например `OPEN → CLOSED`,
   отклоняется.

**Связанные угрозы:** [T-03](THREAT_MODEL.md#t-03),
[T-08](THREAT_MODEL.md#t-08).  
**Проектное решение:** [D-02](SECURITY_DECISIONS.md#d-02).

<a id="sr-05"></a>

## SR-05 — Целостность назначения ответственного

**Свойство.** Назначение ответственного выполняется атомарно сервером. Обычный
пользователь не задаёт ответственного. Специалист не может закрыть обращение,
ответственным за которое является другой специалист, без отдельного явно
разрешённого сценария передачи.

**Критерии приёмки.**

1. Поле ответственного из пользовательского запроса игнорируется или отклоняется.
2. При одновременной попытке двух специалистов принять обращение только один
   становится ответственным; второй получает конфликт без перезаписи результата.
3. Неответственный специалист не может закрыть принятое другим обращение.

**Связанные угрозы:** [T-03](THREAT_MODEL.md#t-03),
[T-08](THREAT_MODEL.md#t-08).  
**Проектное решение:** [D-02](SECURITY_DECISIONS.md#d-02).

<a id="sr-06"></a>

## SR-06 — Ограничение недоверенного ввода

**Свойство.** API проверяет тип, обязательность и допустимую длину заголовков,
описаний, сообщений, заметок и решений. Данные передаются в БД через
параметризованный ORM-доступ и возвращаются как данные, а не исполняемый код.

**Критерии приёмки.**

1. Корректные значения на гранично допустимой длине принимаются.
2. Пустые обязательные поля, превышение длины и неверный тип получают `422` и не
   создают частичных записей.
3. Строка с кавычками и SQL-метасимволами сохраняется как текст и не изменяет
   структуру запроса или посторонние записи.

**Связанная угроза:** [T-05](THREAT_MODEL.md#t-05).

<a id="sr-07"></a>

## SR-07 — Наблюдаемость значимых изменений

**Свойство.** Принятие, закрытие и повторное открытие обращения сопровождаются
неизменяемой через обычный API записью как минимум об обращении, действии,
участнике и времени.

**Критерии приёмки.**

1. После каждого значимого перехода существует запись с фактическим участником
   и временем.
2. Клиент не может назначить другого автора записи аудита.
3. Обычные endpoint продукта не позволяют изменить или удалить запись аудита.

**Связанная угроза:** [T-06](THREAT_MODEL.md#t-06).  
**Проектное решение:** [D-02](SECURITY_DECISIONS.md#d-02).

<a id="sr-08"></a>

## SR-08 — Защита паролей и токенов

**Свойство.** Пароли сохраняются только как стойкие адаптивные хеши с солью.
Токены имеют ограниченный срок действия, проверяемую подпись и минимально
необходимый набор утверждений. Секрет подписи поступает из окружения и не
хранится в Git или ответах API.

**Критерии приёмки.**

1. В БД и журналах отсутствует пароль в открытом виде.
2. Неверно подписанный и просроченный токены получают `401`.
3. Токен не содержит пароль, хеш пароля или секрет подписи.
4. Репозиторий содержит только пример имени переменной секрета, но не рабочее
   значение.

**Связанные угрозы:** [T-04](THREAT_MODEL.md#t-04),
[T-07](THREAT_MODEL.md#t-07).  
**Проектное решение:** [D-03](SECURITY_DECISIONS.md#d-03).

## Проверка полноты

- Идентичность: `SR-01`, `SR-08`.
- Доступ к объектам и служебным данным: `SR-02`, `SR-03`.
- Целостность рабочего процесса: `SR-04`, `SR-05`, `SR-07`.
- Недоверенный ввод: `SR-06`.

Названия состояний, роли, JWT-аутентификация и текущие коды ошибок сверены с
минимальной реализацией. Перед защитой их нужно повторно сверить с зафиксированной
оцениваемой версией.
