# Сценарий защиты EK1

Отдельная презентация не требуется. Этот файл — внутренняя шпаргалка для
репетиции; на самой защите участники отвечают самостоятельно.

## Распределение времени на шесть минут

### 0:00–0:45 — продукт и граница

`M1`:

> Campus Helpdesk — Web API внутренней технической поддержки. Пользователь
> создаёт и отслеживает собственное обращение, специалист принимает его,
> обменивается публичными сообщениями, ведёт внутренние заметки и закрывает
> обращение. В ядро не входят frontend, файлы, email и внешние интеграции.

Показать [назначение и границу](../PROJECT.md#1-назначение).

### 0:45–1:20 — сценарии и граница доверия

`M2` кратко называет три сценария: создание, обработка, повторное открытие.
Главная граница доверия — недоверенный HTTP-клиент/API. Сервер не доверяет роли,
автору, ответственному и состоянию из запроса.

Показать [архитектуру](THREAT_MODEL.md#2-архитектура-и-потоки-данных).

### 1:20–3:10 — центральная цепочка

Рекомендуемая цепочка:

```text
T-02 Раскрытие внутренней заметки
→ SR-03 Конфиденциальность внутренних заметок
→ D-01 Объектная авторизация и разные DTO
→ будущая позитивная и негативная проверка для User и Specialist
```

Нужно объяснить:

1. Пользователь законно видит собственное обращение, но не служебную заметку.
2. Одной проверки роли на endpoint создания заметки недостаточно.
3. Общая ORM-модель может случайно сериализовать заметки в обычном ответе.
4. Поэтому выбраны централизованная проверка и разные публичная/служебная схемы.
5. Цена решения — дополнительный код и синхронизация двух представлений.
6. Проверка сравнивает ответы ролей и отдельно обращается к endpoint заметок.

Показать [T-02](THREAT_MODEL.md#t-02),
[SR-03](SECURITY_REQUIREMENTS.md#sr-03) и
[D-01](SECURITY_DECISIONS.md#d-01).

### 3:10–3:40 — повышенный уровень, если команда его подтверждает

Показать [пограничный случай](THREAT_MODEL.md#7-пограничный-случай-для-проверки-согласованности)
и сравнение вариантов внутри `D-01`.

Не заявлять повышенный уровень, пока оба участника не понимают контрпример,
компромисс и влияние на проверку.

### 3:40–4:20 — запуск

```text
Команда запуска: uvicorn app.main:app --host 127.0.0.1 --port 8000
Команда/запрос проверки: curl http://127.0.0.1:8000/health
Ожидаемый результат: {"status":"ok"}
Автоматизированная проверка: python -m pytest → 6 passed
Фактически проверенный commit/tag: TODO после создания Git-репозитория
```

### 4:20–6:00 — индивидуальные вопросы

Оба участника должны уметь объяснить:

- собственные записи в `CONTRIBUTIONS.md` и связанные коммиты;
- различие `SR`, `T` и `D`;
- почему внутренние заметки требуют отдельного представления;
- почему роль без проверки конкретного объекта недостаточна;
- допустимые переходы состояния;
- что уже реализовано и проверено, а что остаётся будущей проверкой;
- как именно проверялся результат, подготовленный с ИИ.
