# Паспорт проекта

## Общие сведения

**Название команды:** `404 Security`  
**Название продукта:** Campus Helpdesk  
**Коды участников:** `M1`, `M2`  



## 1. Назначение

Campus Helpdesk — внутренний сервис обработки обращений в техническую поддержку
учебной организации. Пользователь создаёт обращение и отслеживает его обработку,
а специалист принимает обращение, ведёт переписку, сохраняет служебные заметки
и фиксирует решение.

Собственная предметная логика продукта включает разграничение публичных
сообщений и внутренних заметок, назначение ответственного специалиста и
допустимые переходы обращения между состояниями. В проекте используются только
учебные аккаунты и вымышленные данные.

## 2. Граница продукта

### В продукт входит

- аутентификация заранее созданных учебных аккаунтов;
- полномочия `User` и `Specialist`;
- создание обращения пользователем;
- просмотр пользователем только собственных обращений;
- просмотр специалистом очереди обращений и принятых им обращений;
- принятие обращения специалистом в работу;
- обмен публичными сообщениями в рамках обращения;
- создание внутренних заметок, доступных только специалистам;
- закрытие обращения специалистом;
- повторное открытие обращения его автором;
- хранение обращений, сообщений, заметок, назначений и состояний;
- регистрация значимых изменений обращения для последующего аудита;
- API-документация и воспроизводимый локальный запуск.

### Внешнее окружение и внешние системы

- HTTP-клиент: Swagger UI, `curl` или другой REST-клиент;
- GitHub как хранилище исходного кода и истории проекта.

Данные хранятся в локальном файле SQLite. Внешние прикладные сервисы и отдельный
сервер базы данных для основных сценариев не требуются.

### Команда сознательно не реализует

- полноценный frontend и мобильное приложение;
- самостоятельную публичную регистрацию аккаунтов и восстановление пароля;
- загрузку вложений;
- чат в реальном времени;
- телефонные обращения и email-уведомления;
- автоматическую классификацию и назначение обращений;
- внешние интеграции;
- аналитику, отчётность и отдельную административную панель;
- реальные персональные или чувствительные данные.

## 3. Пользователи и доступные действия

| Пользователь или роль | Кто это | Что может делать | Что ему недоступно |
| --- | --- | --- | --- |
| `User` | Автор обращения, использующий поддержку | Создавать обращения; просматривать свои обращения; писать публичные сообщения; повторно открывать своё закрытое обращение | Чужие обращения; внутренние заметки; назначение специалиста; закрытие обращения от имени специалиста; изменение автора сообщения |
| `Specialist` | Сотрудник поддержки | Просматривать очередь; принимать обращение; отвечать пользователю; добавлять внутренние заметки; фиксировать решение и закрывать обращение | Действия от имени пользователя; изменение автора обращения; обход допустимых переходов состояния |

Без аутентификации доступен только технический endpoint проверки работоспособности
`GET /health`, не раскрывающий проектные данные, и документация OpenAPI.

## 4. Сквозные сценарии

### Сценарий 1. Создание и отслеживание обращения

- **Участники:** `User`.
- **Начальное условие:** пользователь аутентифицирован; обращения ещё нет.
- **Основные действия:** пользователь передаёт заголовок и описание проблемы;
  сервер определяет автора по аутентифицированному контексту и создаёт обращение
  в состоянии `OPEN`; пользователь запрашивает список своих обращений и открывает
  созданное обращение.
- **Результат:** обращение зарегистрировано, имеет устойчивый идентификатор и
  доступно своему автору.
- **Какие данные или состояние изменяются:** создаётся обращение, сохраняются
  автор, заголовок, описание, состояние и время создания.

### Сценарий 2. Обработка и закрытие обращения

- **Участники:** `Specialist`, `User`.
- **Начальное условие:** существует обращение в состоянии `OPEN`.
- **Основные действия:** специалист просматривает очередь и принимает обращение;
  состояние меняется на `IN_PROGRESS`; участники обмениваются публичными
  сообщениями; специалист при необходимости добавляет внутреннюю заметку;
  специалист фиксирует решение и закрывает обращение.
- **Результат:** решение доступно автору обращения, обращение находится в
  состоянии `CLOSED`, служебные заметки остаются доступны только специалистам.
- **Какие данные или состояние изменяются:** ответственный специалист, состояние,
  публичные сообщения, внутренние заметки, текст решения и журнал изменений.

### Сценарий 3. Повторное открытие обращения

- **Участники:** `User`, `Specialist`.
- **Начальное условие:** собственное обращение пользователя находится в состоянии
  `CLOSED`, но проблема сохранилась.
- **Основные действия:** пользователь добавляет объяснение и повторно открывает
  обращение; состояние меняется на `REOPENED`; специалист продолжает обработку,
  переводя обращение в `IN_PROGRESS`.
- **Результат:** обработка возобновлена без потери предыдущей переписки и решения.
- **Какие данные или состояние изменяются:** добавляется публичное сообщение,
  меняется состояние, сохраняется запись о повторном открытии.

## 5. Значимые данные и другие объекты

| Данные или объект | Для кого имеют значение | Последствия раскрытия | Последствия неправильного изменения, удаления или недоступности |
| --- | --- | --- | --- |
| Обращение и публичная переписка | Автор и специалист | Посторонний узнает описание проблемы и действия пользователя | Искажается запрос или решение; проблема остаётся без обработки; теряется история взаимодействия |
| Внутренние заметки | Специалисты поддержки | Пользователь или посторонний получает служебную оценку и детали диагностики | Специалист принимает решение на основании ложных данных либо теряет контекст диагностики |
| Ответственный и состояние обращения | Автор и специалист | Само раскрытие обычно менее критично, но связывает пользователя с обращением | Подмена оставляет обращение без обработки, позволяет незаконно закрыть его или создаёт ложное впечатление о решении |
| Учётная запись и роль | Все пользователи системы | Раскрытие данных аутентификации позволяет выдать себя за пользователя | Повышение роли или подмена владельца приводит к доступу к чужим обращениям и служебным данным |
| Журнал значимых изменений | Команда и преподаватель при проверке | Может раскрыть метаданные действий | Изменение или удаление мешает установить автора действия и восстановить ход обработки |

## 6. Компоненты и внешние взаимодействия

Актуальная архитектура, потоки данных и границы доверия приведены в
[модели угроз](docs/THREAT_MODEL.md#2-архитектура-и-потоки-данных).

Основные компоненты:

1. HTTP-клиент отправляет учётные данные, команды и проектные данные в API.
2. FastAPI проверяет структуру входа, аутентифицирует пользователя, проверяет
   роль и отношение пользователя к объекту, применяет предметные правила.
3. Слой доступа к данным через SQLAlchemy читает и изменяет состояние в локальной
   SQLite-базе.
4. API возвращает клиенту только поля, разрешённые для его роли и отношения к
   обращению.

Главная граница доверия проходит между недоверенным HTTP-клиентом и API. Сервер
не доверяет переданным клиентом идентификаторам автора, роли, ответственного или
состояния без собственной проверки.

## 7. Откуда продукт получает данные

| Источник | Пример данных | Кто управляет источником | Как продукт использует данные |
| --- | --- | --- | --- |
| Тело HTTP-запроса пользователя | Заголовок и описание обращения | `User` | Создание обращения после проверки формата и длины |
| Тело HTTP-запроса участников | Текст публичного сообщения | `User` или `Specialist` | Добавление сообщения в доступное участнику обращение |
| Тело HTTP-запроса специалиста | Внутренняя заметка, решение | `Specialist` | Сохранение служебной информации с проверкой роли |
| Параметры маршрута | Идентификатор обращения | Любой клиент | Поиск объекта с последующей проверкой доступа |
| Команда изменения состояния | Принятие, закрытие, повторное открытие | Аутентифицированный клиент | Применение разрешённого перехода с учётом роли и текущего состояния |
| Данные входа | Логин и пароль | Владелец учебного аккаунта | Аутентификация; пароль не сохраняется и не журналируется в открытом виде |
| Переменные окружения | URL БД, ключ подписи токенов | Оператор локального окружения | Настройка приложения; секретные значения не включаются в Git |

## 8. Минимальное функциональное ядро

### Обязательные функции

- вход под заранее созданным учебным аккаунтом;
- роли `User` и `Specialist`;
- создание и просмотр собственного обращения;
- очередь обращений и принятие обращения специалистом;
- публичные сообщения;
- внутренние заметки специалистов;
- переходы `OPEN → IN_PROGRESS → CLOSED` и
  `CLOSED → REOPENED → IN_PROGRESS`;
- серверная проверка роли, владельца и допустимости перехода;
- постоянное хранение данных;
- воспроизводимый локальный запуск;
- автоматизированные позитивные и негативные тесты основных полномочий.

### Функции, которые можно исключить при нехватке времени

- поиск и фильтрация очереди;
- приоритет и категория обращения;
- передача обращения другому специалисту;
- расширенная история действий;
- дополнительные поля профиля.

После исключения этих функций сохраняются три сквозных сценария, различимые
полномочия, значимые данные и собственная серверная логика.

## 9. Стек и путь к первой работающей версии

**Основные технологии:** Python 3.12+, FastAPI, Pydantic, SQLAlchemy, SQLite,
pytest.  
**Технологии, новые для команды:** не заявлены.  
**Внешние сервисы, необходимые для запуска:** отсутствуют.  
**Работа при недоступности внешних сервисов:** основные сценарии полностью
работают локально и не зависят от внешних сервисов.  
**Первый технический результат:** реализован минимальный FastAPI-сервис с
health-check, JWT-аутентификацией, ролями, сохраняемыми обращениями, сообщениями,
внутренними заметками и переходами состояния. Все проектные данные сохраняются в
локальном файле SQLite.

Выбор Python должен быть подтверждён при ранней калибровке. Команда обязуется
сохранить автоматизированные тесты, воспроизводимый запуск и требуемые курсом
проверки независимо от выбранного стека.

## 10. Локальный запуск

**Требования к окружению:** Python 3.12 или новее. Отдельный сервер БД не
требуется: SQLite входит в стандартную поставку Python.

**Команды установки и запуска:**

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
export JWT_SECRET='replace-with-at-least-32-random-characters'
export SEED_PASSWORD='replace-with-at-least-10-characters'
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

**Команда или запрос для проверки:**

```bash
curl http://127.0.0.1:8000/health
python -m pytest
```

**Ожидаемый результат:** health-check возвращает `{"status":"ok"}`, Swagger UI
доступен по `http://127.0.0.1:8000/docs`, шесть тестов завершаются успешно.

**Фактическая проверка:** 2 октября 2026 года приложение запущено локально на
Python 3.14.7; `GET /health` и `POST /auth/login` вернули `200`, тесты завершились
результатом `6 passed`.
